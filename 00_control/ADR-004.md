# ADR-004：RUN_FINISHED 生命周期违规判 INVALID_INPUT、pending 统一定义与规格升版 v1.0.2（SPEC_VERSION 1.0.1 → 1.0.2）

- 日期：2026-11-24
- 提出：终审 R3 P1-R3-01、P1-R3-02、P2-R3-03、P2-R3-04（P031 FIX-R3 C 组）
- 决定：采纳（规格修订：可观测行为改变，升版 v1.0.2）
- 状态：已写入规格 v1.0.2；实现见 FIX-R3 A 组（TS）、D 组（Oracle）、B 组（S0 门禁）

## 问题（P1-R3-01 / P1-R3-02）

终审 R3 复现并认定两处阻断：

1. P1-R3-01：严格 Reducer 已发现的 `RUN_FINISHED` 生命周期错误，被
   Planner 的恢复分支主动吞掉。`src/replay/planner.ts:639–688` 的
   `foldTrack` catch 分支在 `PENDING_TOOL_CALL_MISMATCH` /
   `FINISH_WITHOUT_START` / `FINISH_WRONG_RUN` 且事件为 `RUN_FINISHED`
   时，不记诊断、不抛错，而是按 `runId` 找不到时取第一个 `RUNNING`
   run、手动完成目标 run、无条件置全局 `runStatus`，并在
   `outcome.type === "success"` 时把线上
   `event.outcome.pendingToolCallIds` 直接写入派生字段
   `state.pendingToolCallIds`。Oracle 侧
   `oracle/reference.py:1440–1478` 的 `RUN_FINISHED` 分支同样先变异、
   后校验，且无条件置 `state["runStatus"]`：`FINISH_WRONG_RUN`
   （run-2 从未开始）与 `FINISH_WITHOUT_START`（无任何
   `RUN_STARTED`）下 Oracle 仍判 `CONSISTENT, runStatus FINISHED`。
   两侧都对非法轨迹给出 `CONSISTENT`。
2. P1-R3-02：pending 推导口径三处不一致——`src/core/lifecycle.ts:82–97`
   的全局 helper 按 `toolCallId` 分组；`src/core/reducer.ts:207–216`
   的 `reduceRunFinished` 内联检查逐条目过滤、不分组（同一 id 可计
   多次）；`oracle/reference.py:1132–1175` 按 run 与 `toolCallId`
   分组去重。G01 式重复调用下，生产 Reducer 的严格检查与其自身状
   态派生结果自相矛盾（状态说某 id 不 pending，检查却把它计入
   pending）。

另有 P2-R3-03（D-02 两边界无 Golden 覆盖）与 P2-R3-04（代码头注释
仍引 v1.0.0；项目书 §3.4 必填只列 `type`，与 Schema 不一致），见
§6“影响”。

## 决定

### Q1——三条异常路径的裁决：两侧均判 INVALID_INPUT（采纳 (a)，否决 (b)）

**裁决：** `FINISH_WITHOUT_START`、`FINISH_WRONG_RUN`、
`PENDING_TOOL_CALL_MISMATCH` 三条路径下，TS 与 Oracle 均判
`INVALID_INPUT`，诊断码 `INVALID_INPUT`，不新增任何 §6 诊断码。
三码只出现在诊断 message 文本与 `ReducerError` 的 `code` 字段中
作交叉引用（形如 `[FINISH_WRONG_RUN] ...`），不进入 §6 码表，因
此不是规格扩展。

**否决 (b)（记诊断 + 判 INCONSISTENT）的理由：**

1. **Oracle 已有先例且 R3 已背书。** PENDING 在 Oracle 侧已走
   `InvalidInput` 通道（`reference.py:1445–1465`），R3 §3.1 实测
   复现并以此为正确参照；选 (b) 须把 Oracle 的 PENDING 从 raise
   降级为软诊断，等于推翻 R3 已认可的行为与 FIX-R2 的裁决。
2. **裁决对象是输入本身，不是双轨分歧。** 三条路径下 full 与
   resume 两轨看到的是同一条非法 `RUN_FINISHED`，两轨并不彼此
   分歧；§7 对 `INCONSISTENT` 的定义是“双轨状态不同或出现可证实
   的关键故障”（恢复路径故障），而 §7 对 `INVALID_INPUT` 的定义
   是“JSON/SSE 格式错误、必需字段缺失、无法解析的协议事件”——一
   条因无 open run / runId 错配 / pending 声明与状态不符而无法被
   归约的 `RUN_FINISHED`，正是无法解析的协议事件。判
   `INCONSISTENT` 会把“输入轨迹非法”误记为“恢复失败”，误导首分
   歧定位（`firstDivergence` 对非法输入本应为 null）。
3. **不新增诊断码的依据。** §6 所列 10 码中确实没有三码，但本裁
   决不使用它们作诊断码：诊断码沿用 verdict 同名码
   `INVALID_INPUT`，该码已是 Oracle 内部扩展码
   （`reference.py:102–107` 注释：“Oracle extension … not in
   PROJECT_BOOK §6 … Documented here”），且 TS 的
   `evaluateFixture` 失败路径已发出同名诊断码
   （`planner.ts:1248–1252`）。
4. **(b) 在 Oracle 侧不可行。** Oracle 注释（`reference.py:1446–1456`）
   已论证软诊断不可行——full-path 折叠中追加的诊断会被
   `evaluate` 丢弃而 resume 路径会报告，两轨会对同一畸形输入
   给出不同诊断集；只有 raise 才能保证两轨对同一非法输入一致。
5. **TS 侧必须显式映射——拆除回退后 verdict 不会自然成为
   INVALID_INPUT。** 只删除 `planner.ts:649–688` 的回退分支，三码
   将落入同一 catch 的通用分支（`:694–727`），经
   `REDUCER_ERROR_TO_DIAGNOSTIC`（`:176–210`，其中三码在
   `:207–209` 均已映射为 `{OUT_OF_ORDER, CRITICAL}`）记一条
   `OUT_OF_ORDER` CRITICAL 诊断后继续折叠，`classifyDualTrack`
   因 `hasCritical` 判 `INCONSISTENT`——即自然结果是 (b)，不是
   (a)。因此 A 组必须把三码并入已有的显式通道：与
   `UNSUPPORTED_EVENT` / `UNEXPANDED_CHUNK` 同列
   （`planner.ts:690–693`），写为
   `throw new Error(`[INVALID_INPUT] ${error.message}`)`；三码同
   时从 `REDUCER_ERROR_TO_DIAGNOSTIC` 表中删除（Oracle 侧镜像表
   `reference.py:110–146` 亦同步删除），否则后人读表会误以为三
   码仍走 `OUT_OF_ORDER`。

**Oracle 侧改动（D 组）：** `reference.py:1440–1478` 的
`RUN_FINISHED` 分支重写为“检查先于一切变异”：先找 open run
（无则 `FINISH_WITHOUT_START`）、再核对 `runId`（不符则
`FINISH_WRONG_RUN`）、再在 `outcome.type == "success"` 时校验
pending（调用已有的 `_compute_pending_tool_call_ids(state,
run_id=...)`，位置前移），全部检查通过后才执行现有变异。
`FINISH_WITHOUT_START` 优先于 `FINISH_WRONG_RUN`（无 open run
时，即使 `event.runId` 指向一个已结束的 run，也是
WITHOUT_START）；`FINISH_WRONG_RUN` 的判定以 open run 为准，不
以“`event.runId` 是否存在于 runs 中”为准。`cancelled` /
`interrupt` outcome 不做 pending 校验（与 TS
`reducer.ts:204` 一致，维持现状）。

### Q2——pending 统一定义与 TS 统一方案

**规范定义（已写入项目书 §3.14，逐字含义以此为准）：**

> `pending(R)`（R 为一个 run；状态字段 `pendingToolCallIds` 取全部
> run 的并集）是逻辑调用（`toolCallId`）的属性：当且仅当存在至少
> 一条属于 R 的 `toolCalls` 条目，其参数流已闭合（TS：
> `status === "closed"`；Oracle：`not open and not incomplete`），
> 且同一 id 在 R 内的任一条目均未持有结果，该 id 属于
> `pending(R)`。每个 id 在列表中至多出现一次，顺序为该 id 在
> `toolCalls` 数组中的首次出现顺序（即 START 顺序；重开复用条目
> 不改变首次出现位置）。`open`（参数未完）、`incomplete`（run
> 结束时未闭合）、`resulted`（已有结果）的条目均不使 id 进入
> pending；`RUN_FINISHED` 的 `outcome.pendingToolCallIds` 必须与
> `pending(当前 run)` 作为有序数组逐项相等，缺席视为 `[]`。

三处差异逐条核对：**分组**——lifecycle 已分组，reducer 未分组
（可重复计 id、G01 误判），Oracle 已分组，统一后 reducer 与前两
者一致；**作用域**——lifecycle 全局（状态字段正确，RUN_FINISHED
检查错误），reducer 当前 run（检查正确），Oracle 参数化（两者皆
正确），统一后 reducer 保持当前 run 作用域，不得直接调用无参全
局 helper；**顺序**——三处均为首次出现/数组顺序，统一后不变；
**闭合条件**——lifecycle `status === "closed"` 与 Oracle
`not open and not incomplete` 在“结果检查优先”的前提下等价，
reducer 的逐条目条件在单条目视角下等价、错只错在不分组，统一后
闭合条件无需改语义，只改聚合方式。

**TS 统一方案（采纳）：给 `lifecycle.ts:82` 的现有 helper 加可选
run 作用域参数，不另抽新 helper。**

```ts
export function computePendingToolCallIds(state: RejoinState, runId?: string): readonly string[] {
  // 有 runId 时只聚合 t.runId === runId 的条目；无 runId 时全局（现状）。
  // 分组逻辑（Map<id, {hasResult, hasClosed}>、首次出现顺序）一字不动。
}
```

调用点：`reducer.ts:207–216` 的内联过滤整段删除，改为
`computePendingToolCallIds(state, event.runId)`；其余调用点
（`reducer.ts:86`、`lifecycle.ts:664`、`snapshot.ts:504`、
`planner.ts:495、553`）不传参，保持全局语义不变。

**否决备选 1“另抽一个 `computeRunPendingToolCallIds` 新 helper”：**
同一定义出现两个实现正是 P1-R3-02 的成因；ADR-F01 已指定
lifecycle helper 为单一事实源，重复实现必然再次漂移。

**否决备选 2“reducer 内联只加去重”：** 去重后内联与 helper 在文本
上仍是两份定义，下次任一处改动（如闭合条件演进）都会重蹈覆辙；
且内联无法复用 helper 已有的 G01 语义注释与测试。

**Oracle 无需改动 `_compute_pending_tool_call_ids` 本身：** 其分
组/作用域参数/顺序/闭合条件已与上述定义完全一致；D 组只改
`RUN_FINISHED` 分支的调用顺序（检查前移），不改该函数。

### Q3——Planner catch 分支的拆除范围

拆除范围：仅 `src/replay/planner.ts:649–688` 的三码 `if` 分支整段
删除（含其中的 `markOpenItemsIncomplete` 调用、目标 run 选取、
`runStatus` 写入、线上 pending 列表写入、时间线追加）。其余不
动：`UNSUPPORTED_EVENT` / `UNEXPANDED_CHUNK` 重抛通道
（`:690–693`，三码并入此处）；通用诊断映射分支（`:694–727`）；
`REDUCER_ERROR_TO_DIAGNOSTIC` 表中除三码外的全部条目。拆除后
`markOpenItemsIncomplete` 在该 catch 中不再被调用——无损失：非
法 `RUN_FINISHED` 下整个评估以 `INVALID_INPUT` 返回，状态被丢
弃，不存在“需标记未完成条目”的可返回状态；合法 `RUN_FINISHED` /
`RUN_ERROR` 下的调用在 `reducer.ts` 内，不受影响。合法断线/重
连路径不经过 catch（折叠前拦截在 `try` 块之外），拆除不影响任何
合法路径；resume 路径无独立的同类回退（`resolveCheckpoint`、
`buildResumeStream`、`applyInjections` 均不捕获
`ReducerError`），拆除后 full 与 resume 两轨对同一非法
`RUN_FINISHED` 的行为完全一致（均抛错 → `INVALID_INPUT`）。
`foldTrack` 顶部的三码旧注释（约 `:640–648`）随分支一并删除，改
为一句指向本 ADR 的注释。

### Q4——规格版本决策：升版至 v1.0.2（否决“留 v1.0.1 澄清式修订”）

支持升版的决定性事实有四项，每项都超出“澄清”范畴：

1. **可观测裁决改变**：三条轨迹的 verdict 从 `CONSISTENT` 改为
   `INVALID_INPUT`，`fullPath` / `resumePath` 从有值变为 null，
   `firstDivergence` 从可能有值变为 null——这是行为改变，不是文
   字澄清。
2. **归约语义改变**：pending 检查从“逐条目”改为“按逻辑 id 分组
   + run 作用域”，G01 式重复调用下 reducer 的抛错与否会翻转——
   这是算法改变。
3. **原规格确实未决**：§3.14 只写了不变量（“必须与当前 run 中尚
   未收到结果的调用一致”），从未写明违反时的 verdict；TS 与
   Oracle 对同一不变量给出两种 verdict 的事实本身证明原规格欠
   定。ADR-003 更把这两处明文记为“FIX-R2 不改行为、由协调员作
   R3 披露项处理”的已知角落——被披露为已知差异的行为，在下一轮
   被改掉，就是修订，不是 conformance。
4. **先例一致**：v1.0.0 → v1.0.1（ADR-001，§13.2 可空化）是因行
   为/契约改变而升版；ADR-003 保持 v1.0.1 的理由恰恰是“只澄清既
   有语义，不改行为、不升版”——本轮不满足该前提，故不适用同一处
   理。

(甲) 的合理成分予以承认并吸收：§3.14 的不变量文字本身不动，只追
加“定义 + verdict”两句；§3.3 的 run 身份规则本就隐含于“runId
标识一次运行、同一 thread 内不得复用”（§3.3/§4.1），新增的是违
反后果而非身份规则本身。但这不改变升版结论：决定版本的是可观测
行为是否改变，而不是新增文字占原文字的比例。

附带收益：升版强制 `SPEC_VERSION` 全仓同步，新冻结包必然包含新
版规格文本，从机制上杜绝 P2-R3-01/H4 式“Drive 已改、冻结包未改”
的重演；R4 审阅者凭版本号即可区分新旧冻结候选。

§0.5 禁令：新版本条目必须逐项列出改动，不得写“其余冻结内容不
变”——H4 的教训（独立复核 F-03）是该句在 FIX-R2 后即为假
（ADR-003 已对 §5.3/§10.4 加了交叉引用），任何此类总括句都是不
可验证的断言；本轮 §0.5 只列改动条目，不写任何关于未改动内容的
总括句。

## 两类 verdict 的分裂（已裁决，须披露）

三码走 `INVALID_INPUT`，其余 19 个 ReducerError 码仍走
`OUT_OF_ORDER` → `INCONSISTENT`。此分裂是已裁决的事实，不是分
类学上本就如此，R4 必须明文说明，不得假装纯粹。

**为何是这三码而不是全部：** 区分标准不是码的数量，而是违规发
生的位置——三码全部是单条 `RUN_FINISHED` 事件本身无法被归约：
没有可关闭的 open run、目标 run 不是 open run、声明的 pending
列表与当前 run 状态不符。此时折叠无从继续，事件本身就是 §7 所
说的“无法解析的协议事件”，只能以 `INVALID_INPUT` 整体拒绝，状
态被丢弃、无可比路径（`firstDivergence` 为 null）。其余 19 码是
事件可以归约、但在恢复路径上暴露出的顺序/重复/快照类故障
（`CONTENT` 先于 `START`、重复插入、快照不匹配等），归约能够完
成、双轨终态可比，故障以 CRITICAL 诊断记入报告、判
`INCONSISTENT`，首分歧定位才有意义。把三码也判
`INCONSISTENT`，等于要求对一条无法归约的事件伪造终态再比较；
把 19 码也判 `INVALID_INPUT`，等于把可定位、可比较的恢复故障降
级为“输入无效”，丢弃全部路径信息。两者都不诚实。除上述位置标
准外，裁决还同时由三项外部依据支撑：R3 背书（§3.1–§3.3 实测复
现并要求修复）、Oracle 先例（PENDING 已走 `InvalidInput` 通
道）、§7 定义（“无法解析的协议事件”属 `INVALID_INPUT`）。三项
依据与位置标准指向同一结论。

## INVALID_INPUT 诊断的比较口径（门禁）

新三码在 Oracle 侧走固定模板（`Input is invalid: INVALID_INPUT
at sourceIndex ⟨i⟩.`，`sourceIndex` 字段恒为 `None`，见 ADR-003
§4），在 TS 侧走抛错原文（`[INVALID_INPUT] [CODE] ...`，见
`state.ts:413–435` 的 `ReducerError` 构造）。这是 FIX-R2 已接受
的既存不对称（除不支持类型外，Oracle 不复现 TS 内部措辞）。因
此三码夹具的门禁只比粗口径（`code` / `severity` /
`sourceIndex`），不比诊断 message 全文与生产报告哈希（报告哈希
含诊断 message）。A 档夹具（INVALID_INPUT）沿用非法 input 夹具
的粗口径体例；B 档夹具（合法/CONSISTENT）用全口径比对。`INVALID_INPUT`
下 `fullPath` / `resumePath` / `firstDivergence` /
`shortestInjectionSequence` 均为 null，是 `INVALID_INPUT` 的既
定语义（输入非法，无可比路径），不是测试缺失；不得为“补全路
径”而改 verdict。

## 未决点（已知角落，留待后续）

1. **Oracle `RUN_FINISHED` 缺 `threadId` 检查（不纳入 FIX-R3）。**
   TS `reducer.ts:180–186` 对 `RUN_FINISHED` 先查
   `THREAD_MISMATCH`，Oracle `reference.py:1440–1478` 的
   `RUN_FINISHED` 分支无此检查。`threadId` 错配的 `RUN_FINISHED`
   下两侧 verdict 将不一致（TS 经 `THREAD_MISMATCH` →
   `OUT_OF_ORDER` → `INCONSISTENT`；Oracle 可能直接完成 run）。
   R3 未提此项，不属 P1-R3-01/02 范畴；协调员裁决不扩范围，记入
   本 ADR 已知角落留待后续。Oracle 侧加一行镜像检查的改动极小，
   但会改动未被要求的行为、带来新的 parity 风险，故不在本轮做。
2. **D-02a（显式空数组 `toolCalls: []`）：定夺为不修，记为残留已
   知角落。** D 组施工时已按“是否扰动 24 条 Golden 哈希”为界实测
   定夺，决定过程与证据如下：把 `oracle/parity.py:134–135` 的消息
   投影改为“键存在即保留”（`if "toolCalls" in message`）会给每条
   消息都加上 `toolCalls: []`——Oracle reducer 全部 7 处消息创建点
   均默认 `"toolCalls": []`，内部状态无法区分显式 `[]` 与默认值；
   实测 24 条 Golden 的 production 哈希变 23/24、parity 哈希变
   23/24（仅 N05 不变，含 0 条消息）。改动已还原，还原后哈希与基
   线逐字节一致。真正的修复需在 reducer 层记录 wire 是否携带
   `toolCalls` 键（改动内部状态形状、波及 canonical 形式），超出
   备忘录 §2.6 许可范围，故本轮不修。后果：`fixr3_empty_toolcalls`
   夹具退为 A 档式有界断言（verdict + 除该键外的状态哈希一致），不
   得为通过夹具而放宽断言却不披露；显式 `[]` 下 TS 保留、Oracle
   丢弃的差异仍为残留已知角落，留待后续在 reducer 层记录 wire 键
   存在性时一并修复。D-02b（chunk 展开重索引）维持已知角落：FIX-R3
   以专门 parity 夹具覆盖，断言只限 (i) 展开后事件类型与载荷序列相
   等（忽略 `sourceIndex`）、(ii) 两侧 verdict 一致（`CONSISTENT`）
   且终态 parity 哈希相等、(iii) `firstDivergence` 两侧均为 null；
   不得断言两侧展开 `sourceIndex` 序列相等（TS 按发出顺序重编号，
   Oracle 保留原始 index，定义不同）。
3. **chunk 原始定位的长期方案：留待后续。** TS `expandChunks`
   （`src/parser/normalize.ts:1130` 起）丢弃原始下标，
   `firstDivergence.sourceIndex` 在 chunk 轨迹上跨侧不可比。本轮
   只以 (i)–(iii) 有界断言覆盖，不引入原始下标携带；是否在后续
   版本中给展开包装加原始下标字段，由协调员另行立项决定。
