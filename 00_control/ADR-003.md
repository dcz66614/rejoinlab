# ADR-003：完整状态 parity 的 canonical 形式（v1.0.1 澄清，不升版）

- 日期：2026-11-23
- 提出：终审 R2 P1-R2-02（P031 FIX-R2 B 组）
- 决定：采纳（澄清 + Oracle 对齐实现，不是规格语义修订）
- 状态：已实施；S0 门禁 24/24 + 15/15 input + 6/6 parity 夹具全绿

## 问题（P1-R2-02）

终审 R2 §4 指出：parity 只比较缩减投影，不是完整状态 parity。

1. 生产 `projectState()`（`src/core/canonical.ts:411–424`）是 8 个协议
   字段的逐字投影，其中 runs 含 5 个 RunState 字段（`parentRunId`、
   `protocolVersion`、`outcome`、`result`、`error`）；而 parity 投影
   （旧 `gate.test.ts:198–201` 与旧 `oracle/replay.py`）把 runs 缩减为
   `{runId, threadId, status}`，Oracle 根本不存这 5 个字段。反例成立：
   两条仅 `RUN_FINISHED.result` 不同的轨迹，生产哈希不同而 parity
   仍判 PASS。
2. 首个分歧同样算在缩减哈希上（TS `findFirstDivergence` 用生产
   `stateHash`，Oracle `_first_divergence` 用内部 `state_hash`，其 runs
   仍是三元组、messages 丢 owner、toolCalls 含 duplicate）。
3. 报告哈希是第三种哈希，不是生产报告哈希：旧 parity 报告哈希排除诊断
   message/evidence、全部 metrics、input、recovery、assumptions、
   limitations、RunState 元数据、首分歧的哈希与 differences。

## 决定

### 1. 两个投影，一个翻译源

parity 用**两个投影**，共享单一翻译源 `oracle/parity.py`（TS 侧为
`projectState()` + `tests/s0/gate.test.ts` 的 `parityProjectStateTS`）：

- **P——生产投影**：逐字复现 TS `projectState()` 的形状（8 个协议字段，
  TS 构造键序，undefined 丢弃）。用于 Oracle `state_hash`、报告
  `finalStateHash`、首分歧的哈希与 differences（`oracle/diff.py` 逐字
  镜像 `src/core/diff.ts`）、生产报告路径。时间线项的 runId 只在 TS
  有的地方出现（run 事件）。
- **Q——parity 投影**：P 加上**推导出的时间线 runId**（见 §3(b)）。
  用于 S0 parity 终态哈希与 parity 路径。parity 路径 = 生产路径 +
  `runStatus`（§13.2 的生产 `PathResult` 无此字段）。

> 纠正：审计备忘录 §9.2 草案第 2 条称“`state_hash` 与 parity 哈希必须是
> 同一函数”，与本条矛盾——两者不可能是同一函数：生产报告哈希必须复现
> 生产哈希（协调员裁决 2），而 parity canonical 形式携带推导 runId
> （裁决 6）。P 与 Q 共享 `oracle/parity.py` 一个翻译模块，不会悄悄漂移；
> R-11 防护测试断言 parity runs 键集 ⊇ 生产 runs 键集。

### 2. Oracle 存全部 5 个 RunState 字段

- `parentRunId` / `protocolVersion`：RUN_STARTED 两处 run 创建点，有则存，
  缺键时键缺失、绝不存 `None`（JCS 下缺键与 null 字节不同）。
- `outcome`：§3.14 校验通过后整体深拷贝存入。
- `result`：用 `"result" in event` 判断存入——JSON null 是合法
  `JsonValue`，`is not None` 会丢 null；`0` / `false` / `""` /
  `{}` / `[]` 都必须存。
- `error`：仅在有 open run 时存为 `{message, code?}`（N11：任何
  RUN_STARTED 之前的 RUN_ERROR 不产生 run 条目，与
  `reducer.ts:262–266` 一致）。

### 3. Canonical 形式（纠正后的 §9.2 第 3 条）

(a) canonical 形式是生产 `projectState()` 的 8 个协议字段；
(b) **时间线项的 runId 进入 canonical 形式**（纠正备忘录草案 §9.2
第 3(b) 条的自相矛盾——草案写“不进入”，与 §4-Q2b 的 (ii) 裁决直接
冲突）：run 事件取事件 runId，其余项取当前 RUNNING run 的 runId，
无 run 时缺键。推导规则：沿生产时间线走，`RUN_STARTED` 置当前 run，
`RUN_FINISHED` / `RUN_ERROR` 在该项之后清当前 run，其余项取当前
run（无则缺键）。推导出的 runId 追加在项末（parity 专有键，生产
投影中无此位置）。
(c) `runStatus` 保留在 parity 路径中：parity 路径 = 生产路径 +
`runStatus`。
(d) 消息 `toolCalls` 为逐字 wire 对象（旧 id 列表过滤已删除——见
“与备忘录的偏差”第 2 条）；`toolCalls` 键只在非空列表时出现
（显式 `[]` 的角落：TS 保留 `[]`，Oracle 丢弃，无夹具覆盖，见
“已知角落”）。
(e) 诊断、首分歧、visitedStates、BFS 访问数、报告字段的 canonical
形式见 `docs/DIAGNOSTIC_TEMPLATES.md` 与本 ADR §4。

### 4. 报告哈希：完整逐字节复现，不降级

- 生产报告哈希 = TS `buildReport` + `reportHash`（完整报告减
  `metrics.durationMs` 一项），Oracle `oracle/parity.py`
  `report_hash` 逐字复现：诊断含 message/evidence、首分歧完整对象、
  input（含原文 `sourceSha256` 与真实 `sourceFormat`）、recovery
  （可选键缺键编码）、assumptions/limitations（TS 冻结中文文本逐字）、
  `metrics.visitedStates`。
- parity 报告哈希 = 上述生产报告哈希输入中 fullPath/resumePath
  换成 parity 路径（其余字段不变）。
- `visitedStates` = full 折叠历史长 + resume 折叠历史长（TS
  `planner.ts:1331`；错误路径：limit/未知/full 折叠失败 → 0，
  resume 折叠失败 → full 历史长）。
- `bfsVisited` = BFS `evaluateSequence` 调用次数（含初始 `[]` 与超限
  的那一次调用，即超限时 `maxNodes + 1`）；**不进入 JSON 报告**
  （TS `WorkerReportBuild`：“仅 HTML 展示用，不进 JSON”），只作
  门禁对照。
- `bfs_shortest` 返回 `(sequence, visited)`；超限抛出的
  `InvalidInput` 携带 `.visited`。
- INVALID_INPUT 诊断：不支持类型逐字复现 TS 模板
  （`Event at sourceIndex ⟨i⟩ has unsupported or unknown type ⟨JSON⟩:
  not one of the 15 MVP events.`）；其余一律固定模板
  （`Input is invalid: INVALID_INPUT at sourceIndex ⟨i⟩.`，无 index
  时省掉后半句），`evidence {}`。Oracle 内部措辞不进入报告；
  不得静默豁免。FIX-R3 新增三码（`FINISH_WITHOUT_START` /
  `FINISH_WRONG_RUN` / `PENDING_TOOL_CALL_MISMATCH`）同样走此口径：
  Oracle 侧走固定模板，TS 侧走抛错原文（`[INVALID_INPUT] [CODE]
  ...`），门禁只比粗口径（`code` / `severity` / `sourceIndex`），
  不比诊断 message 全文与生产报告哈希（见 00_control/ADR-004.md）。

### 5. Quirks 裁决（协调员定）

- Q1（消息 toolCalls 链接）：(ii) Oracle 复现 TS——不再把流式调用
  attach 到父消息；`_snapshot_message_to_state` 存完整 wire
  `ToolCall` 对象（不再只存 id）。
- Q2a（时间线 TOOL_CALL_START messageId）：(ii) Oracle 复现 TS——
  三处 tool_start 时间线追加在 `parentMessageId` 存在时加
  `messageId`；TS 侧删除规则已删。
- Q2b（时间线 runId）：(ii) Oracle 复现 TS——见 §3(b) 推导规则。
- Q3（内部键名）：(iii) 规格定义 canonical 形式 + 单一翻译源——
  新建 `oracle/parity.py`，`canonicalize_state` 标记 deprecated
  （仍可用，委托给生产投影），`state_hash` 复用生产投影。
- Q4–Q7：(iii) / 已一致，无改动。
- Q8（显式 JSON null 基线与无基线在 null 处碰撞）：只记入
  `docs/LIMITATIONS.md` L-T007-09，不在 FIX-R2 修。

## 与 §5.3 / §10.4 原文的关系

**是澄清，不是语义修订；版本保持 v1.0.1。** §5.3 本就要求完整
parity，§10.4 本就列出终态哈希 + 报告 canonical 哈希 24/24——
旧实现低于规格，FIX-R2 是把实现拉回规格，不是改规格。§5.3 与
§10.4 各加一句指向本 ADR 的交叉引用；不升版、不改任何规格语义。
v1.0.2 触发条件（均未触发）：Q2b 排除合法化、报告哈希降级、Q8
修复、或协调员裁定某处 PROJECT_BOOK 文字改动算作修订。

## 备选方案（已否决）

- 报告哈希降级为“parity 报告投影哈希”（排除诊断文本、metrics、
  input 等）。否决：协调员裁决 2 明确不降级；降级会使门禁放过生产
  报告本身的分歧，违背 §10.4 的 24/24 要求。
- parity 与生产哈希用同一函数（备忘录 §9.2 草案第 2 条）。否决：
  见“决定 §1”——推导 runId 只属于 parity 形式，生产哈希不能含它。
- Q2b 用 (iii) 把 runId 排除写进规格。否决：协调员裁决 6 已定 (ii)；
  排除会使时间线归属在 parity 中不可比。
- 分两批交付（先 Oracle 存字段，后报告哈希）。否决：协调员裁决
  10，§8.3 的 1–8 步一次做完。

## 与备忘录的偏差（实施时纠正，均已向协调员报告）

1. 备忘录 §9.2 §2 自相矛盾（见 §1 纠正框）。
2. 消息 `toolCalls` 的 id 列表过滤**已删除**，未按备忘录 §4-Q1
   建议“保留为防御性 no-op”：存入修复后，消息 `toolCalls` 两侧
   均为逐字 wire 对象；保留过滤会使 parity 弱于生产（不再比较消息
   内完整的 `ToolCall` 对象），且破坏 Q == P + 时间线 runId 的
   差分结构。
3. `relatedSourceIndices`：TS 只在三处携带——`DUPLICATE_TOOL_CALL`
  （`[sourceIndex]`）、`LOST_EVENT`（`[sourceIndex]`）、检查点过期
   `SNAPSHOT_MISMATCH`（`[disconnectAfter]`）；其余诊断一律省略
   （含 `SUSPECTED_DUPLICATE` 与收获诊断）。备忘录初稿个别处写
   `related=[sourceIndex]` 已纠正。
4. `DUPLICATE_TOOL_CALL_RESULT` 映射为 `{DUPLICATE_TOOL_CALL,
   CRITICAL}`（备忘录初稿误记为 OUT_OF_ORDER）。
5. 快照 `toolCalls` 向顶层 `toolCalls` 的同步（TS
   `reconcileMessagesSnapshot` create-only 规则）已在 Oracle 实现，
   不再是未对齐角落。

## 已知角落（不影响冻结夹具，留待后续）

- 显式 `[]` toolCalls：TS 保留，Oracle 丢弃（无夹具）。【FIX-R3
  （v1.0.2）状态：定夺为不修，残留已知角落。D 组实测：把
  `oracle/parity.py:134–135` 投影改为“键存在即保留”会给每条消息
  都加上 `toolCalls: []`（Oracle reducer 全部 7 处消息创建点均默
  认 `"toolCalls": []`，内部状态无法区分显式 `[]` 与默认值），24
  条 Golden 的 production 哈希变 23/24、parity 哈希变 23/24（仅
  N05 不变，含 0 条消息）；改动已还原，还原后哈希与基线逐字节一
  致；真正的修复需在 reducer 层记录 wire 是否携带 `toolCalls` 键
  （改动内部状态形状、波及 canonical 形式），超出备忘录 §2.6 许
  可范围。FIX-R3 以专门 parity 夹具有界覆盖（`fixr3_empty_toolcalls`，
  verdict + 除该键外的状态哈希一致）；D-02a 的 Oracle 投影处理见
  00_control/ADR-004.md。】
- chunk 展开重索引：TS 按发出顺序重编 `sourceIndex` 0..n，Oracle
  保留原始 index（展开后的事件序列一致；门禁只比类型序列与数量）。
  【FIX-R3（v1.0.2）状态：维持已知角落，FIX-R3 以专门 parity 夹具
  覆盖，见备忘录 §2.6 的 `fixr3_chunk_index`：只断言展开后事件类型
  与载荷序列相等（忽略 `sourceIndex`）、两侧 verdict 一致且终态
  parity 哈希相等、`firstDivergence` 两侧均为 null；展开事件的原
  始定位留待后续，见 00_control/ADR-004.md。】
- 无 id 首 chunk：TS 原样通过，Oracle 抛 `InvalidInput`
  （fail-closed）。差异仅在绕过导入校验直接调 helper（`expandChunks`）
  时存在；产品导入路径（TS `normalizeEvents` D-02 / `validateEvent`）
  与 Oracle 均拒绝，线上一致。
- 续 chunk role/name 冲突：TS 忽略，Oracle 抛错。差异仅在绕过导入校验
  直接调 helper（`expandChunks`）时存在；产品导入路径（TS
  `normalizeEvents` D-02 / `validateEvent`）与 Oracle 均拒绝，线上一致。
- `TOOL_CALL_RESULT` role 非 `"tool"`：Oracle 校验层抛
  `InvalidInput`（裁决级）；TS 发 `OUT_OF_ORDER` 诊断——D 组
  校验区域，FIX-R2 不动。差异仅在绕过导入校验直接调 helper/reducer
  时存在；产品导入路径（TS `normalizeEvents` D-02 / `validateEvent`）
  与 Oracle 均拒绝，线上一致。
- `FINISH_WITHOUT_START` / `FINISH_WRONG_RUN` 回退：【FIX-R3
  （v1.0.2）已修复，见 00_control/ADR-004.md】原状态：TS 信任线上
  `pendingToolCallIds` 完成目标 run；Oracle 按 runId 完成而不取线上
  列表——与 §3.3 同族，已实测核实（见完成报告），FIX-R2 不改行为，
  由协调员作 R3 披露项处理。FIX-R3 裁决：两侧均判 `INVALID_INPUT`
  （诊断码 `INVALID_INPUT`），回退分支拆除。
- TS `RUN_FINISHED` pending 校验用**未分组**过滤（G01 式重复条目
  计入），Oracle 用分组计算——同一族差异，见完成报告。【FIX-R3
  （v1.0.2）已修复，见 00_control/ADR-004.md】FIX-R3 裁决：pending
  按逻辑调用分组、当前 run 作用域统一定义（项目书 §3.14），TS 给
  lifecycle helper 加可选 `runId` 参数，不另抽 helper。
